## 0. 走查方法与覆盖清单

### 0.1 本轮要解决的问题

### 0.2 判断标准（用户已定）

1. 回答用户真会问的一个问题，或

## 1. 现状解剖（按任务链路，不按页面）

### 1.1 启动 / 首启

**用户此刻想干什么**：确认工具装好了、要不要现在开启、开了会不会改坏系统。

**界面让他看到什么**：

- 主窗口先出现；约 3 秒后浮出 640×600 的“让 GitHub 快起来”引导。
- 引导包含：一段“部分路径加速，不是全站”的边界说明、当前网络检测结果、4 段“能做什么/不能做什么”、2 个默认关闭的可选项（开机自启、匿名诊断）、底部“先跳过，稍后再说 / 开始加速”。
- 权限说明写在按钮上方：“点击后会开始写入系统网络设置。若当前账号没有管理员权限，系统会弹出一次确认……在你点击之前，不会修改任何系统文件。”

**他会理解成什么**：

- 标题“让 GitHub 快起来” + 关于页“帮助您快速、稳定地访问 GitHub 资源” → 以为这是 GitHub 全站加速。
- “开始加速” → 以为是一个总开关；实际只写 Hosts，且只覆盖部分路径。
- “写入系统网络设置” → 不知道写的是 Hosts，也不知道怎么还原（首启没有“如何撤销”的说明）。
- “匿名诊断信息”被理解为“只报版本号”；设置页却写明采集 CPU/内存/线程数并发送到 `47.113.219.65:6600`。

**需要几次点击**：0 次看到；1 次开始或跳过；开启时另有 1 次 UAC。

**歧义 / 误导 / 死路**：

- **预期被放大**：首启与关于页的措辞比实际能力大；用户随后去 star/issue/push 失败，会归因“加速器坏了”。
- **“跳过也算完成”且无重新入口**：`HasCompletedFirstRunGuide=true` 后不再自动出现；侧栏“使用指南”调用的其实是 `ShowFirstRunGuideAsync`（同一个首启窗），不是 `QuickGuideWindow`；设置里 `ShowQuickGuideOnStartup` 没有对应开关。用户想“下次启动再给我看”只能点“恢复默认”，副作用很大（见 1.7）。
- **旧指南是死代码**：`QuickGuideWindow` 全仓库无调用方，却仍保留“以管理员身份运行”“点击应用”等旧步骤，与首启的“系统会弹一次确认”冲突。若未来有人接回入口，会立刻产生第二套说法。
- **权限说明只在首启完整**：之后在仪表盘点“智能优选”，用户已看不到“会写系统文件”的同等说明。

**误读后果**：首启是用户建立预期的唯一时刻，却同时给出“全站变快”的标题和“部分路径”的正文；后续所有“怎么没变快”的投诉都从这里开始。

### 1.2 判断“我现在能不能用”

**用户此刻想干什么**：GitHub 打不开/很慢，先确认是网络问题、账号问题还是工具没开。

**界面让他看到什么**：

- 首屏 4 张 KPI：`🌐 监控状态（监控中/已停止）`、`⚡ 最佳响应（86 ms）`、`📊 综合评分（92.5）`、`📡 数据源（12 个 / 可用 8）`。
- 一行“应用前延迟 -- ms → 应用后延迟 -- ms = 提升 --”，右侧“重新测速”。
- 快捷栏：`⏹ 停止/▶ 开始`、`🔄 刷新`、10px 的“GitHub 未测试”、`加速状态：未应用`、图标 `✅`、`🗑️`。
- 条件出现：`所有数据源都不可用` 红色失败条。

**他会理解成什么**：

- 绿色“监控中” = 网络正常、加速生效。
- “最佳响应 86 ms” = 打开 GitHub 网页只要 86 ms。
- “综合评分 92.5” = 速度得分（满分多少不知道）。
- “数据源 12 个 / 可用 8” = GitHub 有 12 个入口，8 个能用。
- “GitHub 未测试”字号只有 10px，通常被忽略。

**这些数字的真实含义**：

- “监控中”只表示后台测速计时器在跑（`IsMonitoring`），与 github.com 是否可访问无关；它甚至可以在“所有数据源都不可用”时仍是绿色。
- “最佳响应”是某条镜像线路的平均响应时间（`AverageResponseTimeMs`）。
- “综合评分”是内部加权分（`OverallScore`），公式未在界面公开。
- “可用”= 成功率 > 0.5（`SuccessRate > 0.5`），不是“GitHub 可打开”。

**需要几次点击**：0 次得到 4 个数字，但要用它们拼出答案；要一个真正的“整页能不能开”结论，需要切到“官网访问诊断”（2 次导航 + 1 次重新检测 + 等待）。

**歧义 / 误导 / 死路**：

- **同一屏可以自相矛盾**：上面绿色“监控中”，下面“所有数据源都不可用”；用户不知道该信哪个。
- **真正的可用性指标被埋没**：`GitHubStatusText` 只有 10px，且默认“未测试”；没有“测试 github.com 首页”的主按钮。
- **没有“我现在该做什么”**：4 个数字都不带动作；用户只能继续猜。

**误读后果**：用户在 GitHub 可用时看到“所有数据源不可用”，会以为 GitHub 挂了；在 GitHub 不可用时看到绿色“监控中”，会以为工具认为网络没问题，转去怀疑浏览器/账号，浪费排查时间。

### 1.3 开启加速

**用户此刻想干什么**：让 GitHub 网页、clone、下载变快。

**界面让他看到什么（同一动作的 7 个入口）**：

| 入口 | 文案 | 实际动作 |
|---|---|---|
| 首启 | 开始加速 | 应用最佳源 Hosts |
| 仪表盘主按钮 | 🚀 智能优选 | 拉取全部源，为每个域名选最优 IP 写 Hosts |
| 仪表盘快捷栏 | 图标 ✅ | 应用选中源 |
| 仪表盘列表行 | 应用 | 仅应用此数据源（不合并） |
| 分组管理 | 🚀 应用分组规则 | 写分组规则 |
| 官网诊断 | 防护版 Hosts 加速 → 启用 → 应用 | 只写 github.com，不写 CDN 域 |
| 设置 | 开启 Git 加速 | 改写 Git `insteadOf`，与 Hosts 无关 |
| 下载加速器 | ⚡ 生成加速链接 | 生成第三方镜像 URL，不改系统 |

**他会理解成什么**：

- 所有“加速/应用/启用/智能优选”是一个东西。
- 点 ✅ 和点“智能优选”效果一样。
- “开启 Git 加速”会让网页变快。

**需要几次点击**：主路径 1 次 + UAC；想先看会写什么，需要额外点“预览”（打开源预览窗口）；分组/防护版路径各需 2～3 次。

**歧义 / 误导 / 死路**：

- **图标按钮无文字**：`✅` 与 `🗑️` 只靠 tooltip；`🗑️` 是“清除 Hosts”，属于破坏性动作，却和普通按钮并排等宽。
- **同一页两个“取消”**：快捷栏“取消”是中止正在进行的加速（tooltip 明说不会写 Hosts），列表“取消”是取消全选；用户点错会得到完全不同的结果。
- **“应用”写到哪里、能否撤销，不在按钮附近**：说明散落在首启、设置、官网诊断三处。
- **提权路径只有状态文案**：非管理员点应用后进入“等待提权确认”；若用户拒绝 UAC，界面没有“改用不需要管理员的下载加速”这一替代出口（该能力其实存在于下载页）。

**误读后果**：用户可能以为已经开了网页加速，实际只开了 Git 改写；或误点 🗑️ 把已生效的加速清掉，却以为是“删除某条记录”。

### 1.4 验证“是不是真的变快”

**用户此刻想干什么**：花了一次 UAC、写了一次 Hosts，想知道有没有效果。

**界面让他看到什么（5 套口径同时存在）**：

| 位置 | 指标 | 实际测量对象 | 界面是否标口径 |
|---|---|---|---|
| 仪表盘 | 应用前 / 应用后 / 提升 | 单次请求（代码为 3 次抽样中位数，需管理员，测量时临时移除 Hosts） | 否 |
| 仪表盘 | 最佳响应 86 ms | 某条镜像源的平均响应 | 否 |
| 网络监控 | 当前 / 平均 / 最快 / 最慢 | 每 10 秒 1 次请求（favicon→首页→API 首个成功），不含页面加载 | 是（页标题与页脚都写明），但左侧导航仍叫“网络监控” |
| 子域健康检查 | 每个子域的延迟 | 单个子域请求 | 否；≥300 ms 即“较慢”，≥1000 ms 仍是“较慢” |
| 官网诊断 | 握手中位耗时 | 每个 IP 采样 3 次取中位数，TLS 握手，不含页面资源 | 是，脚注写得很完整 |
| 下载加速器 | 速度徽章 | 镜像 URL 下载吞吐（最多 2 MB / 5 秒窗口） | 部分（tooltip） |

**他会理解成什么**：所有 `ms` 都是“网页打开耗时”；“提升 35%”就是“网页快 35%”；“最佳响应 86 ms”就是“秒开”。

**需要几次点击**：仪表盘“重新测速”1 次 + UAC；网络监控 2 次导航 + 1 次开始；官网诊断 2 次导航 + 1 次重新检测；下载页 2 次导航 + 1 次测速。

**歧义 / 误导 / 死路**：

- **唯一的整页指标被埋在防护版预览里**：默认关闭、要跑 6 组交错配对、且明确“不执行 JS，不等同浏览器”；仪表盘和网络监控主界面都没有它，用户看到的仍是单次/握手毫秒。
- **“重新测速”需要管理员且会临时移除加速**：界面没有提前说明；用户在测速期间打开网页，得到的是未加速结果，却可能把这次体验当成“加速后”。
- **子域“较慢”没有上限**：1.2 秒仍是“较慢”，不会进入“失败”；用户无法判断多慢算不可用。
- **结果不可比**：5 个数字来自 5 种测量（其中下载速度还是 MB/s），散落在不同页面；没有“主指标”告诉用户看哪一个。

**误读后果**：用户按 86 ms 期待秒开，实际整页 2～4 秒，得出“加速没用”；或看到“提升 -20%”不知道这是异常还是正常波动。

### 1.5 遇到失败

**用户此刻想干什么**：失败了，告诉我原因和下一步。

**界面让他看到什么（至少 5 种失败呈现）**：

- 全局底部“失败自救条”（原因 + 一个动作）。
- 仪表盘红色“所有数据源都不可用” + `改用原始链接（关闭加速）/ 重新检测 / ✕ 关闭`。
- 顶栏中央 `StatusMessage`；仪表盘快捷栏又显示同一 `StatusMessage`；另有 Toast 通知。
- 下载页“镜像不可用时的退路”（打开原始链接）。
- 首启“这次没有成功”+ `FailureActionText`；健康检查逐项 `ErrorMessage`；防护版状态提示。

**他会理解成什么**：

- “所有数据源都不可用” = GitHub 全站不可用、工具坏了。
- “重新检测” = 只重新观察一次。
- “改用原始链接（关闭加速）” = 帮我打开原始页面。

**实际动作**：

- “所有数据源都不可用”只说明 12 条镜像源探测失败，直连 github.com 可能仍然可用。
- “重新检测”绑定的是 `ApplyHostsCommand`——**会重新探测并写入 Hosts**，不是只读复检。
- “改用原始链接（关闭加速）”实际是清除 Hosts 加速块，**不会打开任何链接**。
- 同一句状态可能同时出现在顶栏、仪表盘、Toast，措辞还不完全一致。

**需要几次点击**：1～3 次，取决于用户从哪个入口遇到失败。

**歧义 / 误导 / 死路**：

- **按钮名与动作错位**（“重新检测”会写系统文件；“改用原始链接”不会打开链接）。
- **失败原因归并过度**：镜像不可达、本机断网、403 配额（本工具目前无 API 配额场景，但下载/镜像 403 存在）、证书失败可能都落到同一句“网络错误”。
- **没有直达原始链接的出口**：仪表盘失败条里没有“打开 github.com”；下载页有，但只覆盖下载链接。
- **关闭失败条后没有历史**：`✕ 关闭` 后只能等下次检测，日志页才有原始信息。

**误读后果**：用户按“重新检测”以为只是再查一次，结果触发一次系统写入；用户按“改用原始链接”以为会打开网页，结果只是把加速关掉，问题看似“没解决”。

### 1.6 自查自修

**用户此刻想干什么**：工具说有问题，我想自己定位并修好。

**界面让他看到什么**：

- 子域健康检查：`✅ 正常 / ⚠️ 较慢 / ❌ 失败` 三张计数卡 + 每个子域的延迟/错误 + `开始检测 / 复制结果`。
- 官网诊断：只读结论（`ConclusionTitle/Detail`）+ 每个域名的 IP、来源、握手中位耗时、可用性、与基线对比 + 防护版 Hosts 加速（默认关闭）。
- 日志查看：级别、消息、搜索、导出、清空。
- 诊断包：先预览清单与脱敏字段，再导出本地文件。
- Hosts 内容 / 分组 / 备份：查看、编辑、恢复。

**他会理解成什么**：

- “子域失败” = 我的网络坏了；或 = 加速器坏了。
- “较慢” = 还能用；1.2 秒也算“较慢”，所以不用管。
- “官网诊断结论” = 最终答案；但结论页没有“按这个结论去修”的按钮。

**需要几次点击**：至少 4 次页面切换；没有一个结论能直接跳到对应修复。

**歧义 / 误导 / 死路**：

- **结论与动作分离**：健康检查给出“建议切换 Hosts 源”，但按钮不在同一页；官网诊断的只读结论区本身没有动作，修复要用户自己往下滚到“防护版”并理解二次确认。用户要记住结论再找入口。
- **源问题被当成网络问题**：12 条镜像源全失败时，建议“换源”没有意义；界面没有先判断“本机是否断网/直连是否可用”。
- **“较慢”阈值不自洽**：代码为 `<300 ms` 正常，其余一律“较慢”（包括 ≥1000 ms），没有“不可用”档。
- **诊断信息很有价值但入口分散**：日志、诊断包、Hosts 内容、备份各在一个侧栏项下，用户不知道“我该先看哪个”。

**误读后果**：用户按“换源”反复写 Hosts，问题依旧；或把 1.2 秒的“较慢”忽略，直到完全打不开。

### 1.7 停止 / 退出 / 卸载 / 还原

**用户此刻想干什么**：我不想用了，把系统恢复原样。

**界面让他看到什么（至少 7 种“还原”说法）**：

| 说法 | 位置 | 实际作用 |
|---|---|---|
| ⏹ 停止 | 仪表盘快捷栏 | 停止后台测速，不改 Hosts |
| 清除 Hosts（🗑️） | 仪表盘快捷栏 | 移除本程序 Hosts 加速块（需管理员） |
| 改用原始链接（关闭加速） | 仪表盘失败条 | 同上，移除 Hosts 块 |
| 停止加速 | 设置 → Git 设置 | 只撤销 Git `insteadOf` 改写 |
| 撤销 / 恢复首启快照 | 官网诊断防护版 | 只还原 github.com 的固定 IP |
| 恢复到首启前快照 | 备份管理 | 用备份文件覆盖当前 Hosts |
| 恢复默认 | 设置底部 | 只重置应用设置，不回滚 Hosts/Git |

**他会理解成什么**：

- “停止加速” = 所有加速都停了。
- 点窗口 X = 退出程序。
- “恢复默认” = 系统恢复原样。
- 卸载 = 自动清理。

**实际行为**：

- X 关闭按设置隐藏到托盘（`MinimizeToTray` 默认 true），程序仍在运行、Hosts 仍生效；真正的退出只在托盘右键菜单。
- “停止加速”只管 Git，不管 Hosts。
- “恢复默认”立即保存、无确认，把 `HasCompletedFirstRunGuide` 也重置（下次又弹首启），但不会清理 Hosts/Git。
- 仓库内无卸载器；“卸载前请先恢复原始 Hosts”的提示不存在。

**需要几次点击**：要真正“回到原样”，至少 3 个页面、4 个动作；且没有一张清单告诉用户还差什么。

**歧义 / 误导 / 死路**：

- **关窗不等于退出**：用户以为退出，随后卸载/关机，Hosts 块可能残留。
- **“停止加速”是半句话**：用户点完以为全停了，实际只停了 Git。
- **“恢复默认”像系统还原，实际只重置偏好**：还会让首启重新弹出，用户以为设置坏了。
- **无“卸载前还原”入口**：卸载后 GitHub 指向旧 IP，用户不知道原因，也没有工具再帮他清。

**误读后果**：这是本轮最危险的一条：用户按直觉操作后系统仍处于被修改状态，且没有可见的“我还没还原”提示。

| raw | 原始文件 | 仓库里未经网页包装的文件地址 | 下载页 |
| jsDelivr | 静态资源加速节点 | 第三方 CDN，只适合静态文件 | 下载页 |
| Hosts | 本机域名指向表 | 告诉电脑“这个域名去哪个 IP”的系统文件 | 全应用 |
| 数据源 | 加速线路 | 一条可选的加速线路（可能由多个 IP 组成） | 仪表盘 |
| 子域 | GitHub 依赖站点 | GitHub 页面依赖的其他域名 | 子域健康 |
| 基线 | 当前系统解析结果 | 不改任何设置时，本机现在解析到的 IP | 官网诊断 |
| 候选 | 加速线路给出的地址 | 加速方案建议使用的 IP | 官网诊断 |
| 握手中位耗时 | 建立连接耗时（中位数） | 多次连接耗时排序后取中间值 | 官网诊断 |
| 防护版 Hosts 加速 | 固定 GitHub 地址（可撤销） | 只固定 github.com，不碰其他域名 | 官网诊断 |
| 综合评分 | 线路评分（仅详情） | 按成功率/响应算的内部分，不对外当结论 | 仪表盘 |
| 监控中 | 自动测速中 | 只是后台在定时测线路，不代表 GitHub 可用 | 仪表盘/侧栏 |
| 智能优选 | 自动选择最快线路 | 逐域名挑当前最快的 IP | 仪表盘 |
| 应用 | 开启加速 | 把线路写入 Hosts（可撤销） | 仪表盘/分组 |
| 清除 Hosts | 恢复原始访问 | 移除本程序的 Hosts 加速块 | 仪表盘 |
| 诊断包 | 问题报告文件 | 一份脱敏后的本地文件，方便排查/发给作者 | 设置 |
| 代理污染 | 旧的 Git 代理设置 | 以前留下的 `http(s).proxy` 配置 | 设置 Git |
| `✅` / `🗑️` | 启用选中线路 / 恢复原始访问 | 图标改为文字，避免误点 | 仪表盘 |

## 6. 保留指标的四要素

只列建议留在主界面/详情中的指标。缺任何一项的标“待补”，不默认用户懂。

| ID | 指标 | 数值 + 单位 | 含义（一句话） | 统计口径 | 更新方式 | 状态 |
|---|---|---|---|---|---|---|
| K-1 | 可用性结论 | 可用 / 部分可用 / 不可用 | 现在这台电脑能不能正常打开 GitHub 网页、完成 clone | 整页资源加载成功次数 + 关键依赖站点直连结果；不是单次 ping 推断 | 手动“重新检查”，显示检查时间 | **待补**：整页实测能力已有（防护版），但尚未聚合成一句结论 |
| K-2 | 页面加载耗时（主指标） | 秒（如 2.4 s） | 从发出请求到页面资源基本加载完的耗时 | 首页 + 首屏资源；6 组交错配对取中位数；**不执行 JS，不等同浏览器** | 手动实测 | 能力已有（防护版预览），需提升为主界面指标并标口径 |
| K-3 | 建立连接耗时（中位数） | ms | 与某个域名建立安全连接要多久（不含页面内容） | 每个 IP 采样 3 次取中位数；失败样本不参与排序 | 手动“重新检测” | 已有（官网诊断），补人话名 |
| K-4 | 单次请求响应 | ms | 一次请求从发出到收到首字节的时间 | 每 10 秒 1 次；favicon→首页→API 首个成功；不含页面加载 | 实时采样；停止后保留最近值 | 已有（网络监控），需在主界面标口径 |
| K-5 | 下载速度 | MB/s | 从加速线路下载文件的速度 | 最多 2 MB / 5 秒窗口；仅测镜像下载链接，不代表网页 | 点击测速 | 已有（下载页） |
| K-6 | 加速状态 | 已开启 / 未开启 + 当前线路 + 可撤销 | 本机当前是否被写入加速、用的是哪条线路、能否一键还原 | 读本程序 Hosts 块与 Git 改写状态；不推断 | 应用/清除后立即反映；可手动刷新 | 已有（`AccelerationStateText` / `IsHostsApplied`） |
| K-7 | 线路评分 | 0–100 | 仅供排查时比较线路，不作为“能不能用”的结论 | 成功率 + 响应时间的内部加权（公式未公开） | 随数据源刷新 | **待补**：公式公开或标注“内部参考”，且只进详情 |

**必须补的口径说明（当前缺失）**

- 仪表盘“应用前/应用后/提升”：需写明“单次请求、3 次取中位数、需管理员、测速期间临时移除加速”。
- 子域“较慢”：需写明阈值，并增加“不可用”档（否则 1.2 秒仍是“较慢”）。
- “可用”：需写明“最近 N 次成功率 > 50%”，而不是笼统“可用”。

### 12.1 Avalonia `TrayIcon` 替代评估（结论：暂不实施）

| 能力 | 现状（WinForms NotifyIcon） | Avalonia TrayIcon | 风险 / 备注 |
