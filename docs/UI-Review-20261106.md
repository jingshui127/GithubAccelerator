## 必须改（6 条）

### M-1 仪表盘数据自相矛盾 —— 已修
- **位置**：仪表盘 KPI 卡「数据源 0 个 / 可用 0 个」，与同页“已刷新 3 个数据源状态”、推荐卡「GitHub520 567ms 74.6」、列表 1 条并存。
- **现象**：四个数字分别来自不同统计口径；刷新完成仍显示 0。
- **影响**：用户认为数据源全部失效，或以为“监控中”是假状态；直接打击信任。
- **改法**：单一统计源；`可用 N/总数` 与列表 `IsAvailable` 一致；刷新中显示 `—`，完成后一次性刷新；`数据源` 卡改为 `可用 1 / 共 1`。
- **根因（已定位）**：`Sources.CollectionChanged` 的订阅在 `InitializeSourcesFromConfig()` **之后**才挂上，初始化期间加入的 3 个数据源从未触发计数通知，UI 永久停在 0；同时 `RefreshSources` 用 `metrics[i]` 按索引回填（监控结果按评分排序、Sources 按配置顺序，会张冠李戴），推荐卡又取自另一个 `_performanceMonitor` 集合。
- **修复**：订阅提前到初始化之前；检测结果按 URL 回填；推荐项改为 `SelectRecommendedSource(Sources)`（同集合、健康、评分 > 0）；刷新中计数显示 `—`；列表头显示“共 N 个”；无推荐时卡片显示 `—`。
- **证据**：[修改前](screenshots/ui-fix-before-dashboard.png) / [修改后](screenshots/ui-fix-after-dashboard.png)；测试 `DashboardSourceCount_RefreshInProgress_ShowsDashInsteadOfZero`、`DashboardRecommendedSource_EmptyList_ReturnsNothing`、`DashboardRecommendedSource_ComesFromSameListAndRequiresScore`。

### M-2 子域健康检查未检测即显示“失败” —— 已修
- **位置**：子域页首屏 4 行全部红 ✗「失败」，但顶部计数「失败 0」、右上「最近检测 0001-01-01 00:00:00」。
- **现象**：未点「开始检测」就有失败结论；计数与列表矛盾；零值时间直接展示。
- **影响**：新用户第一眼以为 GitHub 全挂；可能直接放弃使用。
- **改法**：未检测状态用灰色「未检测」；计数与行状态同源；时间未测显示 `—`；失败行补一句原因（超时/连接被重置）。
- **修复**：`PENDING` 行延迟文本改为中性灰「— 未检测」；只有检测完成才显示成功/失败色与失败原因；未检测时正常/较慢/失败计数与最近检测时间一律 `—`。
- **证据**：[修改前](screenshots/ui-fix-before-subdomain.png) / [修改后](screenshots/ui-fix-after-subdomain.png)；测试 `HealthCheckItem_Pending_IsNeutralNotFailure`、`HealthCheckItem_FinishedFailure_ShowsFailure`、`HealthCheckViewModel_BeforeAnyCheck_CountsAndTimeAreDash`。

### M-3 网络监控的“真实访问速度”与整页实测冲突 —— 已修
- **位置**：[uireview-09-network.png](uireview-09-network.png)「GitHub 真实访问速度 307ms」；同一时段 curl 实测整页 4.18s、两次 5s 建连超时。
- **现象**：指标测的是低层响应（ICMP/握手），不是整页；命名为“真实访问速度”过度承诺。
- **影响**：用户看到 307ms 会认为已加速成功，实际浏览器仍打不开——这是最危险的误导。
- **改法**：改名「GitHub 接口响应（不含页面加载）」；图下注明“测哪个域名、用什么方法”；若要叫“访问速度”，必须改为整页 TTFB（主域 + 1 个 JS）。
- **修复**：标题改为「GitHub 单次请求响应（不含页面加载）」；图下注明度量口径（每 10 秒对 github.com 单次请求首字节/响应，favicon → 首页 → API 取首个成功）并明确“只代表单个请求，不代表整页打开耗时”，整页对比引导到「官网访问诊断」。
- **证据**：[修改前](screenshots/ui-fix-before-network.png) / [修改后](screenshots/ui-fix-after-network.png)；测试 `NetworkView_Wording_DoesNotClaimRealPageSpeed`。

## 旧版“数据源列表”范式是否值得复用

**值得复用交互，不值得复用评分。**

- **值得复用**：一行一源 + 响应/评分 + 预览 + 应用 + 全选/取消，用户能看懂“选了谁、会发生什么”；这正是当前“加速方式选择”缺的东西。
- **不值得复用**：`SourcePerformanceMonitor` 的响应时间 = **下载 hosts 文件**的耗时（871ms → 61.1 分），评分 = 成功率/耗时/稳定性/条数加权，**与“页面是否变快”无关**；`dns:probe` 的 3827ms 只是查询耗时。用它排序会选出“列表下得快但 IP 很差”的源（本次 GitHub520 就是例证）。
- **建议形态**：保留列表与预览/应用，把“响应”换成“逐域名 TCP/TLS/TTFB 实测”，把“评分”换成“应用后预计整页耗时”，并在预览里列出将写入的域名 + 一键撤销。

## 最大问题
