# 官网访问加速设计（Hosts 优选 IP）

文档状态：M1 已完成（只读诊断面板，不写 Hosts）；**M2 = 可做（防护版）**（依据 §13.3 两时段实测，2026-11-06 16:33 判定）；本轮实施防护版，仍不写 CDN 域
编写时间：2026-11-06（Asia/Shanghai）
适用产品：GithubAccelerator（自用版，无任何上游出口）

---

## 0. 核心判断（先看这一节）

**现状**：当前产品实际是"下载加速器"。官网（github.com 页面浏览、issue/PR、搜索、登录入口）只能靠"镜像版页面"凑合，而 2026-11-06 13:50 实测 ghfast.top 页面路径返回 **HTTP 403 / 14 字节**，99988866 TLS 握手失败，GHProxy 5s 超时——镜像版页面**不能**替代官网浏览（详见 `docs/Optimization_Plan_20261105.md` §十、§十一）。

**本设计定位**：用 **Hosts 优选 IP** 改善"解析层"的官网访问，不引入出口、不装证书、不做 MITM/PAC/内置代理、不改系统 DNS 设置。

**能力边界（必须先讲清）**：

| 类型 | 能否解决 | 说明 |
|---|---|---|
| DNS 解析被污染（解析到错误/不可达 IP） | 能 | Hosts 覆盖系统解析结果，优先级高于 DNS |
| 解析到慢节点 / 解析耗时高 | 能（有限） | 只能选一个 IP，无法按连接动态择优 |
| IP 层阻断、丢包、QoS 限速 | **不能** | 瓶颈在传输层，改解析无效 |
| 需要鉴权且必须连 GitHub 服务器的操作（登录、提交、PR、push） | **不能保证** | 仍依赖到 GitHub 的真实连通性；本方案不改变这一点 |
| github.githubassets.com 等 CDN 静态资源的最优边缘选择 | **可能变差** | 固定单个 IP 会绕过 CDN 调度，见 §8 |

**直连可用时不应强行启用**：2026-11-06 13:31 实测直连 `https://github.com/jingshui127/GithubAccelerator` **200 / 1.56s**（含仓库名特征校验）；而 2026-11-05 21:45 同一路径 **12s 超时**。同一台机器、同一网络，两天结论相反，说明这是**时变**问题，任何"直连不可用"的表述都必须带实测时间。产品默认行为应是：**先测直连，直连可用就不写 Hosts**。

## 1. 域名清单

依据：2026-11-06 13:31 抓取的 github.com 仓库页 HTML 中出现的实际依赖域名（去重后逐条判断），不是凭印象罗列。

| `api.github.com` | 页面内嵌数据请求（贡献者、release、issue 列表等）；未登录也大量使用 | HTML 中出现 | 是（建议，见决策点 6） |

| `user-images.githubusercontent.com` | 仓库内上传图片 | HTML 中出现 | 是 |

### 1.2 下载/归档（浏览非必需，但与现有能力重叠）

| 域名 | 用途 | 现状 | 是否写 Hosts |
|---|---|---|---|
| `codeload.github.com` | 源码 zip/tar 归档 | 2026-11-05 21:45 直连 200/1.23s | 可选（走镜像也可） |

| `objects.githubusercontent.com` | release 资源 302 后的签名地址 | **签名 URL 未取得，未验证** | 可选（Hosts 对签名 URL 有效，但未实测） |

### 1.3 可选（不影响主流程，默认不写）

`gist.github.com`（gist 浏览）、`opengraph.githubassets.com`（分享卡片）、`docs.github.com`（文档站）、`github.blog`、`githubstatus.com`、`desktop.github.com`、`collector.github.com`（遥测，写反而增加无效请求）。原则：**每个多写的域名都增加一次"选错 IP 就坏一处"的概率**，非必需不写。

### 1.4 子资源域名：必须纳入观测（修正，2026-11-06 15:33）

**修正原因**：M1 只测主域，把 `github.githubassets.com`、`avatars.githubusercontent.com`、`camo.githubusercontent.com` 等子资源域名整体排除，导致“候选=基线”的结论只覆盖主域、不能解释整页耗时。页面能否打开 = 主域 HTML + 子资源共同决定，**子资源必须进入观测范围**；但“纳入观测”不等于“默认写入 Hosts”。

| 域名 | 页面中的作用 | 观测要求 | 写 Hosts 条件 |
|---|---|---|---|
| `github.githubassets.com` | CSS/JS 包，决定首屏渲染 | 每次测量必须带一个真实 JS/CSS URL | 仅当实测比系统解析快 ≥30% 才写 |
| `avatars.githubusercontent.com` | 用户/组织头像 | 带一个真实头像 URL | 同上 |
| `camo.githubusercontent.com` | README 外链图片代理 | 带一个真实 camo URL | 同上 |
| `user-images.githubusercontent.com` | 仓库内上传图片 | README 含图时测量 | 同上 |
| `github.io` | 仅页脚链接，非首屏必需 | 可观测、不计入首屏结论 | 不建议写（实测 TLS 被重置，见 §13.2） |

排除在首屏之外的：`collector.github.com`（遥测）、`github.blog`、`docs.github.com` 等，不影响页面打开。

## 2. IP 候选来源

### 2.1 DoH 端点（只读查询，2026-11-06 13:53 实测）

| 端点 | 结果 | 耗时 | 结论 |
|---|---|---|---|
| `https://dns.alidns.com/resolve?name=github.com&type=A` | 200，返回 `20.205.243.166`（TTL 53s） | 0.49s | 可用，作为主候选源 |
| `https://doh.pub/dns-query?name=github.com&type=A`（Accept: application/dns-json） | 200，返回 `140.82.114.4`（TTL 11s） | 0.31s | 可用，作为第二候选源 |
| `https://dns.google/resolve?name=github.com&type=A` | 无响应（curl 000，6s 超时） | 6.0s | 本机不可达，不列入 |

系统 DNS 同日解析结果：`20.205.243.166`（与阿里 DoH 一致，说明**当前未被污染**）。

候选集 = 各 DoH 返回的全部 A 记录（去重），再叠加"当前系统解析结果"作为对照组；不做无来源的 IP 猜测。

**2026-11-06 15:30:44 复测（修正 §2.1 上表）**：阿里 DoH、腾讯 DoH、系统 DNS **三者同时返回 `20.205.243.166`**（腾讯在 13:53 曾返回 `140.82.114.4`，说明 A 记录本身在变）。也就是说，DoH 只给出 **1 个** A 记录时，候选集 = 基线，天然测不出差异；**候选池必须扩展到 GitHub 其他边缘 IP**（见 §13.2 实测）。

### 2.2 第三方公开 hosts 项目数据

**默认不采信，可作补充候选源**（决策点 5）。风险口径修正：改 Hosts 不会导致流量被解密——TLS 仍按域名（SNI + 证书）校验，把域名指向错误 IP 的结果是**握手失败/超时**，不是“明文泄露”。真实风险是：① 数据来源不可审计、更新不可复现；② IP 指向不可达或非 GitHub 的边缘节点，造成超时；③ 指向攻击者控制的 IP 时，攻击者只能拿到连接元数据（IP/端口/SNI/时间），拿不到请求内容与凭据。若要引入，必须满足：明确来源仓库、可校验的提交记录、只取域名→IP 对且不执行其中任何脚本、**必须逐 IP 实测 TCP/TLS 后才写**、与 DoH 结果不一致时以实测为准而不是以列表为准。

**2026-11-06 15:30:33 实测 GitHub520 列表**（`https://raw.hellogithub.com/hosts`，200 / 2.84s / 2476 字节，`# Update time: 2026-11-06T14:51:42+08:00`，抓取时距更新 39 分钟）：格式合法（40 条 `IP 域名`，域名均为 GitHub 相关，IPv4 均合法）；但 `github.com → 20.205.243.166`、`api.github.com → 20.205.243.168` 与阿里/腾讯 DoH **完全相同**，CDN 域名也只是从 DoH 的 4 个 A 记录中任选一个（如 `githubassets → 185.199.109.215`）。结论：**该列表在本次实测中不提供任何新 IP，无法修复当前 github.com 的慢连接**（详见 §13.2）。

### 2.3 不做 SSH / 443 备用端口候选

`ssh.github.com:443` 属于 git 传输通道，与"官网页面浏览"无关；本设计不纳入，避免扩大范围。

## 3. 测速方法

对每个候选 IP、每个目标域名做**应用层近似**探测，而不是只 ping（ping 只反映 ICMP，常被限速或禁用，且不代表 TLS 路径）：

1. `TcpClient.ConnectAsync(ip, 443)`，超时 5s；
2. 成功后在同一个 socket 上 `SslStream.AuthenticateAsClient(域名)`（**必须带正确 SNI**，否则 GitHub 边缘可能直接断开或返回错误证书）；
3. 记录 **TCP 建连耗时 + TLS 握手耗时**，取两者之和为该 IP 的"握手耗时"；
4. 每个 IP 采样 **3 次**，取**中位数**（避免一次冷启动/抖动决定结果）；
5. 并发上限 **4**（避免把本机带宽或对端限流打满，导致排序失真）；
6. 失败判定：TCP 超时、TLS 失败、证书域名不匹配、握手 > 2s，均记为失败；**不允许把失败按 9999ms 混进排序**，应单独计数，且失败样本不参与中位数。

### 3.1 如何避免把 CDN 边缘节点选成"最慢的那个"

- `github.githubassets.com`、`avatars.githubusercontent.com` 走 CDN，不同 IP 代表不同边缘；固定一个 IP 会让部分资源绕远。
- 对策：**分批测量、按域名独立维护**，不共用一张全局 IP 表；CDN 类域名只在"该域名解析结果本身不可用"时才写入，且优先使用该域名自己的 DoH 结果，而不是 github.com 的 IP。
- 判定阈值按域名分别设置（§4.2），避免用一个阈值把 CDN 的 100ms 差异误判为"必须优选"。

### 3.2 2026-11-06 13:54 一次性只读探测（示例，非完整测量）

| IP | 来源 | TCP+TLS（单次） | 结果 |
|---|---|---|---|
| `20.205.243.166` | 阿里 DoH / 系统 DNS | 419ms | OK，TLS 1.3 |
| `140.82.114.4` | 腾讯 DoH | 538ms | OK，TLS 1.3 |
| `140.82.113.4` | 公开 GitHub IP 段（补充候选） | 582ms | OK，TLS 1.3 |
| `140.82.112.3` | 公开 GitHub IP 段（补充候选） | 535ms | OK，TLS 1.3 |

说明：这是单次、单域名（github.com）、未取中位数的冒烟结果，只用于验证"探测方法可行"，**不能**作为优选结论。正式实现必须按 §3 的 3 次采样 + 中位数。

## 4. 选择与准入

### 4.1 选择规则

1. 候选 IP 按 §3 的握手耗时升序排序；
2. 取**最快 N 条**：`github.com` 取 2 条（1 主 1 备，写 Hosts 时由用户选择或按顺序尝试），其余域名各取 1 条；
3. 同分（差值 ≤ 30ms）时优先"系统 DNS 当前返回的 IP"（减少无谓变更）。

### 4.2 健康阈值（建议，需决策点 3 拍板）

| 域名类别 | 准入阈值 | 说明 |
|---|---|---|
| `github.com` | 握手 < 800ms | 2026-11-06 实测 419–582ms，留余量 |
| `api.github.com` | 握手 < 900ms | 与主站同池，略放宽 |
| CDN 类 | 握手 < 500ms 且优于系统解析结果的 30% 以上 | 收益不足则不写 |

### 4.3 全部不合格时的行为

- **不写入任何 Hosts 内容**，不写"一部分"；
- 界面给出：检测时间、每个 IP 的失败原因（超时 / TLS 失败 / 超阈值）、以及一句"本次未做改动，Hosts 保持原样"；
- 保留既有"直接访问 github.com"的原始链接，不自动打开浏览器。

## 5. 写入与回滚

复用现有 [HostsFileManager](file:///E:/CsharpCode/repos/GithubAccelerator/GithubAccelerator.Core/Services/HostsFileManager.cs)，不新建写入通道：

| 能力 | 现有实现 | 本方案如何用 |
|---|---|---|
| 标记块 | `StartMarker` / `EndMarker`（`# === GitHub Accelerator ... ===`） | 只写块内，绝不覆盖块外用户内容 |
| 原子替换 | `ApplyBlockAsync` → `WriteAtomicAsync`（失败则原文件不变） | 整块一次性写入；任一步失败即整体回退 |
| 首启快照 | `WindowsHostsFileService.BackupHostsFileAsync()`（`hosts.backup`）+ `ReplaceAllAsync` 恢复 | 首次写入前快照；"恢复快照"走既有入口 |
| 块级删除 | `RemoveBlockAsync()`（只删标记块，块外顺序不变） | 关闭加速只删块 |
| 被手动修改提示 | `HostsBlockStateStore` 记录 `BlockSha256`，`IsBlockModified` 比对 | 用户改过块内内容时提示"检测到手动修改"，不静默覆盖 |
| 变更记录 | `HostsBlockState` | 扩展记录"前值→后值 IP 列表"（本次新增字段，不影响旧状态读取） |

**每次变更必须记录**：时间、域名 → 旧 IP（或"原无记录"）→ 新 IP、来源 DoH 端点、握手中位数。写入前先备份当前 hosts 内容到状态文件，供"撤销本次"使用。

**绝不**：删改块外行、改系统 DNS 设置、写代理配置、注册开机常驻服务。

## 6. 刷新策略

- **触发条件**：仅启动时检查；缓存有效期 **24 小时**（IP 漂移常见，TTL 实测只有 11–53s，但每次启动都全量测速代价过高）。超期后**仅提示**"可重新优选"，不静默写入。
- **手动刷新**：加速页提供"重新测速"按钮，进度条显示"已完成 X / 共 N 个候选 IP"（沿用现有长任务进度模式）。
- **全失败降级**：不写入、保留现有 Hosts 块不动、给出原因与检测时间；下一次启动重试。
- **不做后台常驻轮询**：不做定时任务、不做托盘后台测速。

## 7. 与镜像策略的关系

两者语义不同，可以并存，但优先级必须写死：

| 场景 | 第一优先 | 后备 | 理由 |
|---|---|---|---|
| 官网页面浏览（github.com 仓库页/issue/搜索） | **直连 + Hosts 优选** | 镜像版页面（仅当页面路径健康检查通过） | 镜像页不是 github.com 本身（登录/交互不可用） |
| git clone/fetch/pull | 镜像 `insteadOf`（默认 gitclone.com，2026-11-06 实测 0.49s） | 直连 | URL 在 DNS 之前就被改写，Hosts 对镜像地址无效 |
| git push | **直连 github.com** | 无 | 镜像不做鉴权转发，push 无法加速（已验证） |
| release / raw 下载 | 镜像前缀 | 直连 / Hosts | 现有能力已覆盖 |

冲突处理：Hosts 条目只影响解析，不改变 `insteadOf` 的改写结果；若镜像域名与 Hosts 域名重叠（不会出现），以镜像改写后的域名为准。

## 8. 风险与副作用

| 风险 | 影响 | 应对 / 不做的理由 |
|---|---|---|
| IP 漂移 | Hosts 条目 1–3 天后失效，表现为超时 | 24h 缓存 + 启动提示重测；不做长期固化；失败时一键"清除加速块" |
| 安全软件拦截写 Hosts | 写入失败或写入后被还原 | 复用现有失败提示与原子写；不尝试绕过、不提权安装驱动、不加白名单 |
| CDN 边缘非最优 | `githubassets/avatars` 变慢，首屏反而更慢 | 纳入观测但不盲写；仅在实测优于系统解析 30% 时才写（§1.4、§4.2） |
| 多网卡 / VPN / 代理 | Hosts 对 VPN 内流量同样生效，可能指向不可达 IP | 检测到活动 VPN/系统代理时**默认不启用**，并提示原因 |
| IPv6 | 只写 IPv4 时，系统可能仍优先走 IPv6 而绕过 Hosts | 第一版**只处理 IPv4**；若系统解析存在 AAAA 且可用，则不改写并说明"当前走 IPv6" |
| 单 IP 无冗余 | 该 IP 故障即全站不可用 | `github.com` 允许写 2 条（同域名多行，系统按顺序尝试）；失败可一键清除 |
| 管理员权限 | 写 `hosts` 需要管理员，普通权限直接失败 | 明确提示"需要以管理员身份运行"，不静默降级、不假装成功 |

## 9. 明确不做

- 不做本地代理 / PAC / 系统代理设置；
- 不做 MITM、不装证书、不解密流量；
- 不改系统 DNS 设置（不写注册表、不调 `netsh`）；
- 不做后台常驻测速/轮询；
- 不自动打开浏览器、不自动跳转镜像页；
- 不采信第三方 hosts 数据（除非决策点 5 明确批准）；
- 不承诺"登录/PR/push 一定能通"；
- 不把"写入成功"表述为"已加速"——只表述为"已写入 N 条解析记录，实测耗时见下表"。

## 10. 测试计划

### 10.1 单元测试

| 用例 | 断言 |
|---|---|
| DoH JSON 解析 | 仅取 A 记录、去重、忽略 CNAME 目标为其他域名 |
| 排序与中位数 | 3 次采样取中位数；失败样本不计入；并发上限生效 |
| 阈值准入 | 低于/等于/高于阈值的边界；全不合格时返回空结果 |
| 原子写与回滚 | 模拟写入失败 → 原文件字节不变；块外内容与行序不变 |
| 半失败 | 3 个域名中 1 个测速失败 → 不写入任何内容（全有或全无） |
| 手动修改检测 | 块内被改后 `IsBlockModified` 为真，界面给出提示 |
| 撤销 | 记录的前值恢复后，hosts 与写入前 SHA256 一致 |

### 10.2 实机测试

1. 记录写入前 `hosts` SHA256 与页面耗时（`curl -w "%{time_total}"`，3 次取中位数）；
2. 写入后重复同样测量，记录域名级耗时对比；
3. 执行"清除加速块"，再次校验 hosts SHA256 与写入前一致；
4. 用非管理员权限复跑写入，确认给出明确失败提示且文件未变。

### 10.3 失败路径

## 12. 待用户拍板的决策点

1. **是否默认开启？** 建议：**默认关闭**。依据：2026-11-06 13:31 直连 200/1.56s，属"可用"，强行启用可能引入负收益；只在用户点"测一下"后给出建议，再由用户手动写入。
2. **刷新间隔？** 建议：**24 小时**（启动时检查 + 手动刷新），不做后台轮询。DoH TTL 只有 11–53s，频繁刷新没有意义且增加写 Hosts 次数。
3. **准入阈值？** 建议：`github.com` 握手中位数 < 800ms；CDN 类"优于系统解析 30% 且 < 500ms"；全不合格不写。
4. **是否同时写 `api.github.com`？** 建议：**写**，但只在它自己测速合格时写；未登录页面大量依赖它，缺了它首屏数据会失败。
5. **是否采信第三方公开 hosts 项目？** 建议：**只作候选池，不直接写**（不可审计/不可复现；错误 IP 的后果是握手失败，不是明文泄露）。必须逐 IP 实测 TCP/TLS 后才写入；本次实测 GitHub520 与 DoH 同 IP，不提供增量（§2.2、§13.2）。
6. **是否写 CDN 域名（githubassets/avatars/camo）？** 建议：**必须观测，但不盲写**；只有某 IP 实测优于系统解析 ≥30% 才写，避免固定 IP 破坏 CDN 调度（§1.4）。
7. **IPv6 怎么处理？** 建议：第一版只写 IPv4；检测到 AAAA 记录可用时提示"当前走 IPv6，未改写"。
8. **写两条 `github.com` 记录做冗余？** 建议：**允许 2 条**（主备），代价是同域名多行在部分系统上只取第一条，需在界面说明"第一条生效"。

### 14.7 整页度量与 20% 准入（2026-11-06 18:5x 小修）

#### 14.7.1 为什么必须换指标（实测证据）

2026-11-06 17:19 的旧口径预览选中 `140.82.112.3`：5/5 成功、TCP 中位 251ms、TTFB 252ms，按“TCP < 0.5s”完全合格。但随后在该机器上模拟应用后实测整页为 **2.538s / 6.148s / 10.996s**，而当时直连为 **0.776s / 0.783s / 0.855s**。单次握手/首字节不能代表整页；旧指标会把“建连快、整页慢”的 IP 选出来，宣称“加速”却实际变慢。这是本轮改口径的直接原因。

#### 14.7.2 方法、实现与局限

- 方法：`HttpPageLoader.MeasureAsync` 先 `GET https://github.com/`（`SocketsHttpHandler.ConnectCallback` 只把 `github.com` 固定到候选 IP，TLS 仍按域名做 SNI），读回 HTML 并校验 2xx + 内容特征（≥512 字节且含 `<html`/`github`）；再用 `HtmlSubResourceParser` 按出现顺序提取前 10 个 `<script src>` 与 `rel=stylesheet` 的 `<link href>`，去重、跳过 `data:`，以最多 6 并发拉取；`TotalMs` = HTML + 子资源墙钟总耗时，`TotalBytes` = HTML + 子资源解压后字节；子资源域（githubassets 等 CDN）走正常 DNS，不 pin、不写 Hosts。
- 子资源不决定“页面是否可达”：HTML 2xx + 内容校验通过即 `Success=true`；单个子资源 5s 超时或整体预算耗尽只计入 `SubResourceFailedCount`，不会把一个“HTML 已打开、个别资源慢”的页面判死。若 HTML 本身失败/超时/内容校验失败，则整次采样失败。
- 选优：每个候选整页最多 3 轮，首次失败即停止以省超时；成功率 ≥ 90% 且整页中位存在才合格，按整页中位排序。TCP/TLS/TTFB 仍做 3 次诊断并展示在明细/块注释中，但**不参与资格与排序**。
- 局限（不得宣称等同浏览器）：不执行 JS、不跑布局/渲染，因此没有 FCP/LCP/TTI；无浏览器缓存、Service Worker、预连接/预加载；不模拟 HTTP/2 多路复用/优先级与连接复用（每次采样新建连接池）；只取前 10 个 JS/CSS，不含图片/字体/XHR；子资源域解析取决于本机 DNS；`TotalBytes` 是解压后字节，不等同网络流量。该指标只用于候选相对比较。

#### 14.7.3 20% 准入与超时例外

- 常规：候选整页中位必须 ≤ 直连整页中位的 80%（即快 ≥ 20%）才 `AdmissionAllowed=true`；否则 `ApplyAsync` 直接拒绝并返回人话原因，含候选/直连中位数字与检测时间（例：“拒绝应用：候选 … 整页中位 900ms，直连 1000ms，快 10%（要求候选快 ≥20%）；检测时间 2026-11-06 18:00:00。”）。
- 例外（故障转移）：直连整页不可用（3 轮成功率 <90% 或全失败/无法解析）时，不要求算 20%；只要候选整页可达（2xx + 内容校验通过、成功率 ≥90%）即可应用。这样“直连正在超时/失败”的真实场景不会因“没法算 20%”被拒。
- 准入结论在预览时给出并显示在界面；`ApplyAsync` 对 `AdmissionAllowed=false` 的旧计划再次拒绝，避免绕过 UI 直接调用。

#### 14.7.4 种子来源与自动观测

- 内置种子保留来源与加入时间；`20.27.177.113` 的来源/备注补充实测：2026-11-06 17:19 预览实测 **TCP 65ms、TTFB 238ms（0.065s 级）**，另有 17:19 前的 M1.5 两时段最快记录。
- `OfficialSiteSeedStore.RecordObservation`：**只在复测/自愈时**写入观测——复测健康或切换成功时，把当前 IP 的整页中位/字节/时间写回其种子（已存在只更新“最近实测”字段，不改原来源与加入时间）；预览严格只读，不写 Hosts、也不写种子文件。无来源、私有/非法 IP、非正数耗时一律拒绝。种子仍只来自内置/手动导入/复测观测，不做批量未标注抓取。

#### 14.7.5 flaky 根因与 5 轮结果

- `ExportImport_Roundtrip` / 导出导入相关：根因是**测试隔离缺陷**。`HostsGroupService`、`DataExportImportService`、`OperationHistoryService` 是进程级 `Lazy<T>` 单例；`HostsGroupServiceTests.Clear_RemovesAllGroups` 会在并行运行的其它测试类执行期间清空全局分组，`OperationHistoryServiceTests` 构造/Dispose 也清空全局记录。导出方虽然已对分组做 `Snapshot`，仍可能在“创建测试数据 → 导出”之间被另一个测试清空，导致往返断言失败。修法：新增 `GlobalStateCollection`（`DisableParallelization=true`）并把这些会改全局单例的测试类放入同一串行集合；删除往返测试里的 `Task.Delay(100)`（`ExportAsync` 已 await 完成，延时是纯时间依赖）。另给 `OperationHistoryService` 的读写加锁、`Records` 返回快照，消除导出枚举与 `Record` 并发修改的真实线程安全隐患（产品侧小修，不改变功能）。
- `RunAsync_RespectsConcurrencyLimit`：根因是**测试错误假设并发完成顺序**。服务用 `SemaphoreSlim` 正确限制 probe 并发（实测 ≤3），但多个 IP 完成时 `Interlocked.Increment` 的先后与 `IProgress.Report` 追加到列表的先后不一致；测试却断言“列表最后一条的 CompletedIpCount == TotalIpCount”，线程调度一换就可能最后追加的是较早完成的计数（实测失败为 Expected 4 / Actual 2）。修法：改为断言不依赖顺序的不变量——每条 `TotalIpCount==4`，且存在 `CompletedIpCount==4` 的进度项；并保留 `MaxConcurrent <= 3`。未放宽并发上限断言、未加重试。影响面：该错误断言此前会随机红，但不会掩盖产品缺陷；产品并发限制本身正确。
- M2 后的“时序抖动”：即上述导出往返的 `Task.Delay(100)` + 全局单例并行清空，以及并发进度顺序假设；已按上两条修掉。守卫版测试全部使用临时目录与内存 fake，不依赖真实网络/系统 Hosts/时间延时。
